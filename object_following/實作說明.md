## 1. 官方原始碼的問題

官方 `execute(change)` callback 的完整邏輯只有這些：

```python
def execute(change):
    image = change['new']

    # 1. 碰撞避障模型判斷是否被擋住
    collision_output = collision_model(preprocess(image)).detach().cpu()
    prob_blocked = float(F.softmax(collision_output.flatten(), dim=0)[0])
    blocked_widget.value = prob_blocked

    if prob_blocked > 0.5:
        robot.left(0.3)          # 被擋住就左轉，跳過所有跟隨邏輯
        image_widget.value = bgr8_to_jpeg(image)
        return

    # 2. 偵測所有物件
    detections = model(image)

    # 3. 篩出 label 相符的框
    matching_detections = [d for d in detections[0] if d['label'] == int(label_widget.value)]

    # 4. 選離畫面中心最近的一個
    det = closest_detection(matching_detections)

    # 5. 沒選到就往前走，選到就轉向跟隨
    if det is None:
        robot.forward(float(speed_widget.value))
    else:
        center = detection_center(det)
        robot.set_motors(
            float(speed_widget.value + turn_gain_widget.value * center[0]),
            float(speed_widget.value - turn_gain_widget.value * center[0])
        )
```

對照畢專的伴護需求，有五個實質問題：

| # | 問題 | 後果 |
|---|---|---|
| 1 | **完全沒有記憶** | `closest_detection()` 每一幀獨立重選「離中心最近」的框，不記得上一幀跟的是誰。走廊上任何人只要走到畫面中央，機器人就換人跟 |
| 2 | **沒有鎖定概念** | 一偵測到人就立刻開始跟。長輩還沒準備好、或只是路過鏡頭，機器人就衝上去 |
| 3 | **找不到人時盲目前進** | `robot.forward()` 在沒有任何候選框時直接往前開。對伴護場景這是最危險的行為——看不到人反而加速前進 |
| 4 | **沒有任何使用者回饋** | 目標者不知道自己有沒有被鎖定、系統現在是什麼狀態 |
| 5 | **避障只有左轉** | 沒有「繞不過去」的概念，也沒有通知照護者的機制 |

另外文件與程式碼不一致：notebook 說明文字寫 "Person (index 0)"，但程式碼是
`label_widget = widgets.IntText(value=1)`。依需求文件第 110 行，**以程式碼為準**
（TF Object Detection API 的 COCO label map 中 person 是 1，0 保留給 background），
本次改寫維持 `value=1` 未動。

## 2. 架構決策：為什麼拆成三層

原本可以全部塞進 notebook 的一個 cell，但拆成三支檔案：

```
follow_state.py    決策層  純標準函式庫，不 import jetbot / torch / cv2 / GPIO
feedback.py        輸出層  LED、蜂鳴器、照護者通知
sonar.py           輸入層  HC-SR04（選配，預設關閉）
live_demo_*.ipynb  接線層  取影像 → 問狀態機 → 執行動作
```

**理由一：可以在筆電上測。** `follow_state.py` 不碰任何硬體，所以 `test_follow_state.py`
在一般電腦上就能跑完 15 組測試。時間是當作參數餵進去的（不是 `time.time()`），
所以「連續 0.75 秒」「被擋 8 秒」這種條件都在毫秒內測完，不用真的等，更不用佔用機器車。

這件事在開發過程中直接證明有價值：測試抓到三個真實錯誤（見第 8 節），
如果只能在車上測，這三個都要靠現場反覆試才找得到。

**理由二：狀態機不知道硬體存在。** `update()` 回傳一個 `Action`，描述「該做什麼」，
而不是自己去動馬達：

```python
Action = namedtuple('Action', ['state', 'motor', 'steer', 'target', 'events'])
```

- `motor`：`'stop'` / `'steer'` / `'turn_left'` / `'forward'`
- `steer`：差速用的水平偏移量
- `events`：這一幀發生的事件字串（`'lock_acquired'`、`'notify_no_target'`…）

notebook 拿到 `Action` 之後才決定要接哪個馬達指令、要不要響蜂鳴器、要不要推播 LINE。
所以要換硬體（例如蜂鳴器改成震動馬達）不會動到決策邏輯，要改決策邏輯也不會弄壞硬體。

**理由三：事件而非直接呼叫。** 狀態機不呼叫 `beep()`，而是產生 `EVENT_LOCK_ACQUIRED`。
這讓「蜂鳴器只在鎖定完成時響」變成一條可驗證的規則——測試只要檢查事件列表，
就能確認跟丟、繞行、無法跨越這些情境**沒有**產生該事件。

## 3. 狀態機總覽

```
                    目標置中且夠近            連續 0.75 秒
   ┌─────────┐ ──────────────────> ┌────────────┐ ─────────> ┌────────┐
   │ waiting │                     │ confirming │            │ locked │
   └─────────┘ <────────────────── └────────────┘            └────────┘
        ^          目標離開/不合格                                 │
        └──────────────── 跟丟超過 2 秒寬限 ─────────────────────┘

   任一狀態被擋住
        │
        v
   ┌────────┐  轉開   ┌────────────────┐  橫移完成
   │ detour │ ──────> │ detour(advance)│ ──────────> 回到原狀態
   │ (turn) │         └────────────────┘
   └────────┘
        │
        │ 判定繞不過去（三條件任一）
        v
   ┌──────────────────┐
   │ impassable_wait  │ ──── 障礙排除 ────> 回到原狀態
   └──────────────────┘
```

### 狀態對應的行為

| 狀態 | 馬達 | LED | 蜂鳴器 | LINE |
|---|---|---|---|---|
| `waiting` | 停止 | 慢速閃爍 | 無聲 | 連續 3 秒沒人才通知 |
| `confirming` | 停止 | 快速閃爍 | 無聲 | 「鎖定確認中」（30 秒節流） |
| `locked` | 差速跟隨 | 恆亮 | **短鳴一聲**（進入的那一刻） | 「已完成鎖定」 |
| `detour` | 左轉 → 直行 | 恆亮 | 無聲 | 不通知 |
| `impassable_wait` | 停止 | 慢速閃爍 | 無聲 | 「遇到無法跨越的障礙」 |

`detour` 的 LED 維持恆亮而不閃爍，是刻意的：繞行期間鎖定並沒有解除，
對目標者而言「還跟著你」的訊息不該改變，閃爍會被誤解成出了問題。

### 蜂鳴器的唯一使用時機

需求文件第 112–113 行明訂：蜂鳴器只在「鎖定完成」響一次。跟丟重新鎖定、
無法跨越障礙都不對目標者發出警示音。

設計原則是**不應把系統的問題轉嫁成要求目標者做出反應的負擔**——機器人繞不過去
是機器人的事，對著長輩嗶嗶叫只會造成焦慮，卻不能改變任何結果。該通知的是照護者。

這條規則有專門的測試守著（`test_buzzer_only_on_lock`）：跑完一整段包含鎖定、
跟丟、重新鎖定、目標消失的流程，統計 `EVENT_LOCK_ACQUIRED` 只能出現一次。

## 4. 逐項實作說明

以下對照需求文件「落差分析」表格的九個項目。

### 項目 1：跨幀連續性追蹤

**官方**：每幀獨立選最近的框。
**改為**：比對候選框與上一幀鎖定框的位置與大小，選最像的延續。

核心是 `_continuity_cost()`：

```python
def _continuity_cost(self, bbox, prev_bbox):
    """與上一幀鎖定框的相似度成本，超出門檻回 None。"""
    cx, cy = bbox_center(bbox)
    px, py = bbox_center(prev_bbox)
    dist = math.sqrt((cx - px) ** 2 + (cy - py) ** 2)
    if dist > cfg.track_center_max_dist:      # 位置差太多，不可能是同一個人
        return None

    h, ph = bbox_height(bbox), bbox_height(prev_bbox)
    ratio = h / ph if h > ph else ph / h
    if ratio > cfg.track_height_ratio_max:    # 大小差太多（一個近一個遠）
        return None

    return dist + 0.5 * (ratio - 1.0)         # 成本越小越像
```

回傳 `None` 表示「這個框不可能是上一幀那個人」，直接排除。有通過的框裡選成本最小的。

鎖定目標存成物件而不是裸 bbox：

```python
class LockedTarget(object):
    def __init__(self, bbox, signature, now):
        self.bbox = bbox
        self.signature = signature   # v1 為 None；v2 存 re-ID 特徵
        self.locked_at = now
        self.last_seen = now
```

`signature` 現在永遠是 `None`，但欄位先留著——見第 6 節。

### 項目 2：鎖定啟動狀態機

三個條件全部滿足才算鎖定：

```python
def qualifies_for_lock(self, bbox):
    if abs(center_offset(bbox)) > cfg.center_tolerance:   # 水平置中 ±15%
        return False
    if bbox_height(bbox) < cfg.min_bbox_height:           # 距離夠近
        return False
    return True
```

加上第三個條件「連續維持 0.75 秒」，由 `_update_unlocked()` 計時：

```python
if now - self._confirm_started >= cfg.confirm_seconds:
    signature = self.signature_fn(image, det['bbox'])
    self._locked = LockedTarget(det['bbox'], signature, now)
    self.state = STATE_LOCKED
    events.append(EVENT_LOCK_ACQUIRED)    # ← 蜂鳴器唯一的觸發點
```

**倒數期間也要驗證是同一個人**，否則甲站了 0.5 秒走開、乙立刻站過來，
會接續甲的計時而提早鎖定：

```python
if self._continuity_cost(det['bbox'], self._confirm_bbox) is None:
    self._confirm_started = now          # 換人了，重新計時
    events.append(EVENT_CANCEL_CONFIRMING)
    events.append(EVENT_ENTER_CONFIRMING)
```

`waiting` 和 `confirming` 兩個狀態下機器人都**原地不動**（`MOTOR_STOP`），
等目標自己走到鏡頭中央站定。不是機器人追著人跑去對準。

### 項目 3：LED / 蜂鳴器回饋

需求已定案改用 LED + 蜂鳴器，不用 LCD 文字。實作在 `feedback.py`。

閃爍**不開執行緒**，直接用時間相位計算，避免拖慢 camera callback：

```python
def update_led(self, state, now):
    if state in (STATE_LOCKED, STATE_DETOUR):
        on = True                                                 # 恆亮
    elif state == STATE_CONFIRMING:
        on = (now % LED_FAST_PERIOD) < (LED_FAST_PERIOD / 2.0)    # 快閃 0.2s
    else:
        on = (now % LED_SLOW_PERIOD) < (LED_SLOW_PERIOD / 2.0)    # 慢閃 1.0s
    self._write_led(on)
```

`_write_led()` 只在狀態改變時才真的送 GPIO，避免每幀重複寫入。

蜂鳴器用 `threading.Timer` 關掉，**不能用 `time.sleep()`**——callback 每幀只有
66~100ms 預算，睡 0.15 秒會直接掉幀：

```python
def beep_locked(self):
    GPIO.output(self.buzzer_pin, GPIO.HIGH)
    self._beep_timer = threading.Timer(BEEP_SECONDS, self._buzzer_off)
    self._beep_timer.daemon = True
    self._beep_timer.start()
```

### 項目 4：跟丟後重新鎖定

原鎖定框對不上任何候選框，但畫面中還有其他人時，退而選離中心最近的：

```python
# 項目4：對不上任何延續框 → 退而選畫面中離中心最近的候選框。
# 已知風險：這裡沒有身分驗證，可能跟到路過的人（v1 接受此限制）。
fallback = min(candidates, key=lambda d: _dist_from_frame_center(d['bbox']))
```

`select_target()` 回傳 `(detection, matched_previous)`，第二個值告訴上層這是延續
還是重新鎖定。重新鎖定時發出 `EVENT_RELOCKED`，而 `handle_events()` **刻意不為
這個事件接任何輸出**——不響蜂鳴器，也不打擾照護者。

### 項目 5：畫面中完全沒人

**官方**：`robot.forward()` 盲目前進。
**改為**：原地停住 + 通知照護者。

```python
if det is None:
    # 項目5：畫面中完全沒有候選框 → 原地等待（不前進）
    if now - self._locked.last_seen > cfg.lost_grace_seconds:
        self._locked = None
        self.state = STATE_WAITING
        events.append(EVENT_LOCK_LOST)
    return self._act(MOTOR_STOP, 0.0, None, events)
```

有 2 秒寬限期：偵測模型偶爾漏一兩幀是正常的，不該因此要求長輩重新站定一次。
超過寬限才真的解除鎖定。

通知需要節流，否則 10fps 下每秒會打 10 次 API：

```python
def _track_absence(self, candidates, now, events):
    if candidates:
        self._absent_since = None
        return
    if self._absent_since is None:
        self._absent_since = now
        return
    if now - self._absent_since < cfg.no_target_notify_delay:   # 連續 3 秒才算
        return
    if self._should_notify(self._last_no_target_notify, now, cfg.notify_cooldown):
        self._last_no_target_notify = now                       # 60 秒 cooldown
        events.append(EVENT_NOTIFY_NO_TARGET)
```

### 項目 6：避障與跟隨的銜接

官方的 early-return 優先權覆蓋架構本身符合設計，維持不變。唯一要處理的是：
避障結束後要**銜接回上一次的鎖定框**，而不是重跑一次鎖定流程。

問題在於避障期間 `update()` 根本沒被呼叫，跟丟計時會照跑，避障超過 2 秒寬限
就會被判定跟丟。解法是避障期間呼叫 `on_blocked()`，它會凍結計時：

```python
def on_blocked(self, now):
    if self._locked is not None:
        self._locked.last_seen = now     # 凍結跟丟計時
    self._absent_since = None
    ...
```

測試 `test_blocked_preserves_lock` 守著這件事：避障 3 秒（超過 2 秒寬限）之後，
狀態仍是 `locked`，且不需要重新站定。

### 項目 7：無法跨越的障礙

**設計決策：不需要額外的樓梯感測器。** 碰撞避障模型只回答「擋住/沒擋住」就夠了，
因為 JetBot 對樓梯和牆角一樣過不去，不需要分辨是哪一種。

改用時間特徵判定，三個條件任一成立即判定繞不過去：

| 條件 | 判定方式 | 抓什麼情況 |
|---|---|---|
| (a) | 連續被擋 ≥ 5 秒 | 正對牆壁、樓梯，轉都轉不開 |
| (b) | 8 秒滑動視窗內被擋比例 ≥ 50% | 左右來回擺盪（見第 5 節） |
| (c) | 連續繞行 ≥ 3 次仍過不去 | 障礙物比橫移距離寬 |

判定成立後進入 `impassable_wait`：停止、通知照護者、**不對目標者發警示音**、
保留鎖定等目標回來。

### 項目 8：跌倒偵測

依需求文件第 111 行，MPU-6050 IMU 的跌倒偵測**不在本模組範圍**，另開獨立模組，
不與 camera callback 合併。本次改動完全沒有碰。

### 項目 9：馬達參數

`speed_widget` / `turn_gain_widget` 滑桿保留供現場調整，數值待孩童與長者分別實測。
未做動態調整。

## 5. 繞行與擺盪：最麻煩的一段

這一段是整個改寫中花最多時間、也最容易被誤解的部分，值得單獨說明。

### 問題：官方的左轉不會產生位移

`robot.left(0.3)` 是左右輪反轉：

```python
def left(self, speed=1.0):
    self.left_motor.value = -speed
    self.right_motor.value = speed
```

這是**原地自轉**——車體位置完全沒有改變，只有車頭朝向轉了。系統也沒有記錄
原本的行進路線，避障結束後純粹靠跟隨邏輯把車頭拉回目標。

所以當障礙物（例如地上一顆石頭）正好落在機器人與目標者之間：

```
1. 石頭擋住          → 原地左轉
2. 轉到不擋住了      → 跟隨邏輯算出目標在右邊，差速右轉
3. 轉回正對目標      → 也正對石頭
4. 又被擋住          → 回到 1
```

機器人在石頭前面左右擺盪。目標者可以直接跨過石頭繼續走，機器人過不去。

### 錯誤的第一版解法

最初只做了條件 (a)「連續被擋 5 秒就判定繞不過去」。這**完全擋不住擺盪**——
擺盪時是「擋住 → 沒擋住 → 擋住」，`_blocked_since` 每次都被重置，
永遠累積不到 5 秒。機器人會無限卡在原地，而且不會通知任何人。

### 正確的解法：承諾

關鍵認知是：**擺盪的根因不是「不知道有障礙」，而是轉開之後沒有任何承諾，
下一幀立刻被跟隨邏輯拉回原方向。**

這代表加裝超音波感測器**也不會解決擺盪**——只要架構沒改，感測器再準也一樣來回。

解法是新增 `detour` 狀態，分兩階段：

```python
def _continue_detour(self, now, events):
    if self._detour_phase == DETOUR_TURN:
        # 這一幀沒被擋住 = 已經轉開了，開始橫移
        self._detour_phase = DETOUR_ADVANCE
        self._detour_advance_started = now
        events.append(EVENT_DETOUR_ADVANCE)

    if now - self._detour_advance_started < cfg.detour_advance_seconds:
        # 橫移期間凍結跟丟計時：目標可能暫時不在畫面中央甚至出框，
        # 但這是我們自己轉開造成的，不該因此判定跟丟。
        if self._locked is not None:
            self._locked.last_seen = now
        self._absent_since = None
        return self._act(MOTOR_FORWARD, 0.0, None, events)      # ← 強制直行

    # 橫移完成，交還給跟隨邏輯
    self.state = STATE_LOCKED if self._locked is not None else STATE_WAITING
    events.append(EVENT_DETOUR_DONE)
    return None
```

`advance` 階段強制直行 1.5 秒，**期間完全不理會目標的拉力**。這 1.5 秒是車體
唯一真正產生橫向位移的時候。

測試 `test_detour_commits_before_rejoining` 專門守這件事：目標明明就在正前方 0.5，
轉開後仍必須先橫移，不能立刻 `MOTOR_STEER`。

### 保險：擺盪偵測

繞行不一定成功（障礙物可能比橫移距離寬），所以保留條件 (b) 當保險：

```python
def _is_thrashing(self, now):
    history = self._block_history
    if len(history) < 2:
        return False
    # 必須累積滿一整個視窗才下判斷
    if history[-1][0] - history[0][0] < cfg.block_window_seconds:
        return False
    blocked = sum(1 for _, is_blocked in history if is_blocked)
    return (float(blocked) / len(history)) >= cfg.block_ratio_threshold
```

即使被擋是斷斷續續的，只要 8 秒內超過一半的幀都被擋住，就判定繞不過去。

### 超音波的定位

`sonar.py` 是**選配，預設關閉**（目前硬體只有 LED + 蜂鳴器）。團隊定案是架設於與
LED、蜂鳴器**相同高度**、朝向車體前方，用途是**量測該高度上的前方距離**。

所以它的角色是測距，不是「補相機看不到的東西」。它提供碰撞模型給不了的資訊——
一個實際的距離數值。碰撞模型是二分類，只回答「擋住／沒擋住」，沒有距離概念，
因此無法支援「幾公分內就停」這類絕對門檻。

它的貢獻**不是**修擺盪。修掉擺盪的是 `detour` 的橫移承諾，那是純時間邏輯，
不依賴任何感測器。

融合用 **OR 而不是加權平均**：

```python
def is_blocked(prob_blocked, distance_m, prob_threshold=0.5, distance_threshold=0.35):
    if prob_blocked > prob_threshold:
        return True
    if distance_m is not None and distance_m < distance_threshold:
        return True
    return False
```

兩者給的是不同性質的資訊，不是同一件事的兩個估計值，各自也有不同的失效情況——
碰撞模型的判斷取決於訓練資料涵蓋了哪些場景，超音波的錐狀波束僅約 15 度且對斜面、
布料等吸音材質會漏測。加權平均之後任一方的警告都會被另一方稀釋，結果是照樣撞上。
這與需求文件「避障與跟隨為優先權覆蓋架構，不是加權混合」的安全考量一致。

`distance_m` 為 `None`（未啟用、故障或超出量程）時一律當成「不知道」而非
「前方淨空」，不因此放行。

測距開在**背景執行緒**：一次量測最久要等 timeout（2 公尺約 12ms），
而 callback 每幀只有 66~100ms 預算還要跑兩個神經網路，同步量測會吃掉超過一成。

## 6. re-ID 接縫設計

項目 4 的已知風險是跟丟後可能跟錯人。完整解法是 re-ID（外觀特徵比對），
但深度 re-ID 模型在 Jetson Nano 4GB 上要與現有的兩個模型（AlexNet 碰撞避障 +
SSD MobileNet 偵測）競爭記憶體與算力，成本不合畢專時程，因此**延到 v2**。

延後的前提是**現在就把接縫留好**，否則之後要加會變成大改。留了四個點：

**1. 鎖定狀態用物件，不用裸 bbox**
`LockedTarget` 已經有 `signature` 欄位，v1 填 `None`。

**2. 所有目標選擇走同一個函式**
`select_target(candidates, image)` 是唯一的選擇入口，加 re-ID 只是在裡面多一道過濾。

**3. `image` 從第一天就傳進去，即使 v1 根本不用**
這是最重要的一點。官方的 `closest_detection()` 只吃 bbox list，沒有原始影像。
re-ID 一定要拿框去 crop 原圖，如果現在沒把 `image` 串進選擇路徑，
之後要補就得一路往上改參數。

**4. 身分驗證失敗的分支現在就寫進狀態機**

```python
if locked is not None:
    if self.identity_score(image, fallback['bbox'], locked) < cfg.identity_threshold:
        return None, False       # 寧可原地等，也不跟錯人
```

v1 的 `identity_score()` 永遠回 `1.0`、門檻 `0.0`，所以這條路徑永遠不會走到。
但它已經存在、已經被測試覆蓋。

### v2 上線只需要三行

```python
sm.signature_fn   = lambda image, bbox: 抽取特徵(image, bbox)
sm.identity_score = lambda image, bbox, locked: 比對相似度(...)
config.identity_threshold = 實測門檻
```

`test_reid_seam_rejects_stranger` 已經驗證這件事：把 `identity_score` 換成回傳 0.0、
門檻調到 0.5，跟丟時的行為自動從「選最近的繼續跟」變成「原地等待」，
狀態機一行都沒改。

### v2 建議做法

第一版做 **HSV 顏色直方圖**：鎖定時取框高 20%~55% 區域（上半身，避開臉與腳）
算直方圖存進 `signature`，重新鎖定時用 Bhattacharyya distance 比對。
運算約 1~2ms，不載入任何模型，擋得掉「長輩穿米色、路人穿黑色」這類多數情境。

深度 re-ID（OSNet 等）列為未來工作。

## 8. 開發過程中測試抓到的三個真實錯誤

這三個都是寫完程式、跑測試才發現的，值得記錄——它們證明了離線測試的價值。

### (1) 追蹤測資寫得不切實際

第一版的連續性追蹤測試讓目標在單一幀內從 0.50 跳到 0.62，同時讓路人站在正中央 0.50。
測試失敗。

檢查後發現**錯的是測資不是程式**：那種情況幾何上本來就分不出來
（正是需要 re-ID 才能解的 case）。實際 10fps 下人是逐幀漸移的，鎖定框會跟著移動。
改成逐幀移動（0.54 → 0.58 → 0.62）後，「延續框勝過離中心最近的框」才是有意義的驗證。

**教訓**：測試失敗時要先判斷是程式錯還是測資錯，不要反射性地改程式去迎合測試。

### (2) 連續時間門檻擋不住擺盪

見第 5 節。第一版只做了「連續被擋 5 秒」，寫擺盪測試時才發現這個條件在
斷斷續續被擋的情況下永遠不會觸發。這是設計缺口，不是實作 bug——
測試逼出了原本沒想到的失效模式。

### (3) 擺盪偵測誤判合法繞行

加上滑動視窗偵測後，`test_normal_corner_turn_is_not_mistaken_for_impassable` 失敗：
合法的 2 秒繞行結束後恢復跟隨，在視窗只有半滿時被擋比例仍達 50%，
好端端繞開的轉角被判定成死路。

修法是把判定條件從「半個視窗」改成「必須累積滿一整個視窗」：

```python
if history[-1][0] - history[0][0] < cfg.block_window_seconds:
    return False
```

代價是判定變慢（最壞情況先擺盪約 8 秒才停下），但避免了把正常轉彎誤判成死路。
這個 trade-off 是刻意的。

## 10. 已知限制與後續工作

### 待現場實測校正的參數

集中在 notebook 的「載入狀態機與回饋硬體」那一格，詳見 `README.md` 的參數表。
最重要的是 `min_bbox_height`（距離門檻）——notebook 會把目標框高比例印在畫面左上角，
實測時直接讀。

### 三個已知限制

**1. 跟丟後可能跟錯人**（項目 4 的已知風險）
v1 不做身分驗證。解法與接縫見第 6 節。

**2. 繞行是開環的**
橫移時間是固定值，系統不知道自己實際偏開多少，也不知道障礙物有多寬。
石頭小就過得去，障礙寬一點就過不去。靠三重放棄條件安全失敗。
要閉環需要左/中/右三顆超音波，才能選空曠那側繞、並確認障礙已通過。

**3. 判定繞不過去最慢要 8 秒**
這是第 8 節 (3) 那個 trade-off 的代價，換取不誤判正常轉彎。

### 部署前必須確認

1. **LED / 蜂鳴器的 GPIO 腳位**（`feedback.py` 的 `LED_PIN` / `BUZZER_PIN`）
2. **`label_widget` 是否正確框到人**（程式碼是 `1`，notebook 文字寫 `0`，以程式碼為準但要實測）
3. **照護者通知管道**——LINE Notify 官方服務已於 2025-03-31 終止，
   需改用 LINE Messaging API 的 push message 或既有 MQTT，再用 `feedback.set_sender()` 掛上

### 排程中的後續工作

- **感測器融合**（HC-SR04 + MPU-6050）：排在硬體串接跑通、機器車能順利跑之後才測試。
  `sonar.py` 與接線說明已備好，屆時把 notebook 的 `ENABLE_SONAR` 改成 `True` 即可，
  狀態機不用動
- **re-ID**：見第 6 節。建議與距離門檻校正**共用同一次錄影**
  （目標者走動 + 不同衣色路人 + 各種光線），不要跑兩趟
- **跌倒偵測**（MPU-6050 IMU）：獨立模組，不併入本 callback
